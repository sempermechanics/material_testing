# Network calls and enqueues allowed on a screen's lifecycleScope, checked by
# scripts/check_activity_scope_work.py (TD-228, ADR-016 rule 1).
#
#   path (under app/src/main/java/com/sempermechanics/semper/) | function | call | reason
#
# `function` is the one holding the launch (or the property it initialises),
# `call` as the check prints it. An entry that matches nothing fails the check,
# so this list only shrinks. Every reason names a TD- or ADR- pointer.
#
# Triaged 2026-10-19, on the branch after #457 moved Home's restore and sign-in
# to ViewModels.

# ── Refreshes: a read the screen repeats on its own or on the next tap ──────
# Not a request the user can lose (ADR-016 amendment): a rotation cancels it and
# the recreated screen, or the user's next tap, asks again.

ui/auth/PendingApprovalActivity.kt | checkStatusAgain | refreshStatus | Status read behind the "check again" button; a rotation stops it and the next tap repeats it, nothing is written (ADR-016 amendment: a repeated refresh)
ui/home/HomeCloudCheck.kt | queue | CloudSync.reconcile | Home's list refresh (moved out of HomeActivity for TD-227), the example the ADR-016 amendment names; every onResume requests it again
ui/settings/SettingsAnalysesSection.kt | analysesRefresh | CloudRestore.listCompleted | The analyses list read; a recreated Settings loads it again (ADR-016 amendment: a repeated refresh)

# ── Enqueues that cannot be lost by a cancel ─────────────────────────────────

ui/settings/SettingsCloudSection.kt | maybeOfferBackfill | CloudSync.enqueueUpload | The enqueue runs in the confirm dialog's click handler, not in the coroutine that showed the dialog; nothing on the scope enqueues (TD-228 heuristic: lambdas are not told apart)
ui/home/BackupBadgeActions.kt | enqueueBackup | CloudSync.enqueueUpload | The PENDING stamp is on disk before the enqueue, and the next reconcile re-queues a PENDING row (data/cloud/CloudReconcile.kt repairRows, requeue); ADR-016 rule 3 holds for the upload itself
ui/settings/SettingsAnalysesSection.kt | startBackup | CloudSync.enqueueUpload | Same as Home's Back up: PENDING stamped first, re-queued by the next reconcile (CloudReconcile.repairRows); ADR-016 rule 3 holds for the upload itself
ui/settings/SettingsYourDataSection.kt | observeConsent | setImprovementConsent | A false positive: the match is SettingsViewModel.setImprovementConsent in the switch listener that showConsent installs; the send itself runs on viewModelScope (ADR-016 rule 1, TD-228 heuristic: lambdas are not told apart)
